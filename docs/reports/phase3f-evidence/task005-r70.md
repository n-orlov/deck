Tip before: `366dd78` (task 004, R69 legs 2+3), so this lands **on top of** R69's rewritten
`terminal` guard, not beside it. Toolchain: `ci/run.sh` (`deck-ci:local`).
`/proc/loadavg`: `3.10 3.01 3.67` (revert-and-reproduce run), `3.17 3.03 3.67` (green package run),

## The fix: one clause, in the transaction that already clears `killed_by_user`

`internal/store/lease.go`, `AcquireLaunchLease`'s acquisition `UPDATE`:

```sql
 SET status = 'starting', killed_by_user = 0,
     pane_exit_status = NULL, crash_tail = NULL,
     launch_lease_owner = ?, launch_lease_until = ?
```

Nothing else changed. In particular:

- **`store.go:650`'s `COALESCE` is untouched** — first-writer-wins on a crash verdict still holds for
  writes that go through `UpdateSessionStatus`. The clear lives in the resume transaction instead,
  which is the only place that knows a *new* pane is about to replace the described one.
- **`store.go:610`'s hook guard is untouched** — a hook write of `running` is still dropped while
  `pane_exit_status` is set. It is correct for the case it was written for (a genuine crash verdict on
  the *current* pane); once the column is cleared on resume it is correct as written.
- `git diff --stat` for the product change is exactly `internal/store/lease.go | 23 ++++++--`
  (the SQL clause plus the doc comment); `internal/store/store.go` and
  `internal/service/reconcile.go` are not modified at all.

## `crash_tail` retention decision: cleared, deliberately

Cleared, for two reasons and one non-reason:

1. **It has control-flow meaning, not just diagnostic meaning.** The reconciler's `terminal` gate
   reads `PaneExitStatus`, and the TUI renders `CrashTail` as the durable crash artifact for the row.
   A tail describing a pane that has been replaced would caption a live, freshly launched session with
   the last words of a dead one — a wrong answer displayed with full confidence, which is the class of
   defect #9 is about.
2. **Forensics already live where forensics belong.** The crash stays on the record as the
   `tmux.pane_dead` event, whose reason names the exit status (`tmux pane exited with status 137`), and
   the audit log carries the matching transition. Nothing is lost by clearing a session *column*.
3. The non-reason: retention was not declined for convenience. If richer forensic retention is ever
   wanted, the PRD's own guidance applies — it belongs in `events`, not in a column the reconciler
   reads.

## Tests (both required legs, plus the column write itself)

| test | guard pinned | where |
|---|---|---|
| `TestResumeMakesACrashedRowReconcilableAgain` | guard 1, `reconcile.go`'s `terminal` skip | `internal/service/resume_crash_verdict_test.go` |
| `TestResumedRowAcceptsTheNewPanesFirstHook` (`SessionStart`, `UserPromptSubmit`) | guard 2, `store.go:610` | `internal/hookrecv/resumed_crash_verdict_test.go` |
| `TestAcquireLaunchLeaseClearsTheReplacedPanesCrashVerdict` | the column write, incl. raw `NULL`ness | `internal/store/lease_test.go` |

Both required tests **drive a post-launch transition**, as the PRD demands — neither reads the status
straight after `launch.ready`, which passes on unfixed code because `starting` is genuinely correct at
that instant.

- The hook leg asserts on the **status column** (`running`/`hook`/`status_at`), and separately asserts
  the event landed *either way* (count 1 both before and after the fix) — that asymmetry is exactly
  the trap in the operator's transcribed row: `session_start` present in `events` at 07:25:10 while
  `status_at` still read the previous day.
- The reconcile leg's fixture is built through real code paths: a real pane exits 137, a real
  `svc.Reconcile` pass collects it (storing `pane_exit_status` + `crash_tail`, killing the corpse), and
  the row is really killed via `svc.Kill` — the only in-app route back to a leasable row, since
  `AcquireLaunchLease` refuses any status but `stopped`. The fixture asserts it is discriminating
  (stopped **and** still carrying the previous pane's verdict) before resuming. The row is a `shell`
  so that "observed, not skipped" has an observable consequence: the `starting → running` promotion,
  its `tmux.shell_live` event (count 1) and its audit line. The observation assertions come **before**
  the column assertions on purpose, so unfixed code fails on the behaviour rather than on the cause.
