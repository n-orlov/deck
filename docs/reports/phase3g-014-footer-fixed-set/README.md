# Task 014 — curate the footer's fixed set, regenerate the golden frame

SPEC §11.3: "The footer's fixed set is curated for the keys worth a whole line of the
frame. It carries navigation, `↵`, `a`, `Y`, `n`, `x`, `r`, `R`, `dd`, the eligible one
of `A`/`U`, `,`, `i`, `?` and `q`. Rarely-used per-row actions — the permission switcher
`P`, pin `p` — stay bound, stay in the `?` overlay and in §11's keymap, and stay out of
the footer."

## The change

`footerLegend` (`internal/tui/tui.go`), in SPEC's own order:

- Removed the `P` (profile) and `p` (pin) entries outright.
- Added `dd` (delete) between `R` and the archive slot — `footerRowEligible(m, true,
  canDelete)`, batch-aware like `x` (help text: "the mark set non-empty, x and dd act on
  the whole batch"). `canDelete` has no per-session refusal, so it shows for any
  non-empty selection.
- Added `A`/`U` as one mutually-exclusive slot: `A` uses a new **footer-only**
  predicate, `footerArchiveEligible` (`session.ArchivedAt == 0`), and `U` keeps using
  the existing `canUnarchive` (`ArchivedAt != 0`) — exact complements, so exactly one of
  the two ever renders for a given row, per SPEC §11.3's own examples ("`A` on a row
  that is already archived, `U` on one that is not" are the cases the footer never
  lists). `footerArchiveEligible` is deliberately **not** wired into the `case "A"` key
  handler — `canArchive` (used there) stays unconditionally true, unchanged; whether
  pressing `A` on an already-archived row should itself be refused is a different,
  out-of-scope question this task does not touch.
- Added `,` (settings) as a global entry (`eligible: nil`, like `n`/`?`/`q`) — SPEC:
  "`,` because settings has no other visible entry point in the default frame."

`P`/`p` stay bound (`case "P"`/`case "p"` untouched) and stay documented in the `?`
overlay (`helpText`'s "Keys" section — `TestEmptyAndHelpViewsAreDiscoverable` already
pins `"P switch the permission profile"` / `"p pin"` there) and in §11's keymap
(SPEC.md:1145-1150, protected/read-only, unchanged — it already named every key on both
sides of this diff).

## The golden frame

`features/testdata/golden/side_by_side_80x24.golden` regenerated with:

    ci/run.sh env UPDATE_GOLDEN=1 go test -count=1 ./features/ -run TestGoldenMinimumFrame

**The regenerated bytes are byte-identical to the pre-task-014 checked-in file** (same
sha256, `git diff` empty) — this is expected, not a sign the regeneration did nothing:

- The fixture's one row is deliberately pinned at status `starting` (the fake-claude
  fixture's "silent" mode, `golden_frame_test.go`'s own pre-existing comment: "never
  emits any of internal/agent's probe markers... deterministic, not a race to wait
  out"). This choice predates task 014 and stays as-is — changing it is out of this
  task's scope.
- At 80 columns, that row's footer legend already elides after its third entry
  (`↑/↓ · Enter interactive · a attach · …`) **before** reaching the point in
  `footerLegend`'s order where `dd`/the `A`/`U` slot/`,` sit (they come after `R`, and
  `R` itself is already past the cutoff for this row). `footerLegendWithin`'s algorithm
  accumulates kept entries left-to-right and stops at the first one that would overflow
  the budget — entries dropped for running out of room are dropped regardless of what
  they are, so removing `P`/`p` and inserting `dd`/`A`-or-`U`/`,` later in the list
  changes nothing about what was already being cut off before the first three entries'
  width was even reached.
  - Confirmed directly: `footerLegendWithin`/`footerKeyLegend`'s unit tests above
    (`footer-and-parity-tests.log`) exercise the exact same eligibility/elision code
    path this golden frame's footer line runs through, at both 80 and 200 columns, and
    show `dd`, `A`, `,` rendering in full once there is room — the golden frame not
    showing them is a width/eligibility fact about *this one row's* status, not evidence
    the new entries fail to render.
- Regenerating and re-running (`golden-regen-and-pass.log`) reproduces the identical
  sha256 twice in the same run (`TestGoldenMinimumFrame`'s own run-1/run-2), and passes
  against the checked-in file with no `UPDATE_GOLDEN` afterward, per the task's own
  success criterion.
