# R139 probe audit — `default_group_first` (GH #34)

Method: a scratch git worktree (`git worktree add .scratch-r139 HEAD`, HEAD ==
`b7d7b7d`, the tip of R139's three landed commits — 001 `0ef480f`, 002
`4911855`, 003 `b7d7b7d` — over the launch sha `2752c9e`) with only R139's
*product* hunks reverted, one probe's hunk at a time, test files left exactly
as they landed. Each run is `ci/run.sh go test -count=1 <pkg> -run <Test>`.
The worktree was restored to a clean `git status --porcelain` and removed
before this report was written; the fixed tree's own
`ci/run.sh go test -count=1 ./internal/tui/ ./internal/config/` is green
(`ok internal/tui 7.224s`, `ok internal/config 0.041s`).

## Probe 1 — group order with the flag set

**Test:** `TestGroupOrderDefaultFirstFlagTrueMovesStructuralDefaultAloneToFront`
(`internal/tui/group_default_first_test.go`) — asserts `m.groupSessions()`
over groups `aaa`, `zzz`, the structural default (`""`) and a user-created
group literally named `Default`, with `DefaultGroupFirst: true`, orders them
`["", "aaa", "Default", "zzz"]`.

**Product hunks reverted:** commit `4911855`'s only product hunk,
`internal/tui/group.go` — `groupSortsBefore` back to its original two-string
signature (no `defaultFirst` parameter) and `groupSessions`'s call site back
to `groupSortsBefore(groups[i].Name, groups[j].Name)` with no third argument.
Test files (`group_default_first_test.go`, which already calls the
three-argument form) left untouched.

**Exact failure produced** (`ci/run.sh go test -count=1 ./internal/tui/ -run TestGroupOrderDefaultFirstFlagTrueMovesStructuralDefaultAloneToFront -v`):

```
FAIL	github.com/n-orlov/deck/internal/tui [build failed]
FAIL
# github.com/n-orlov/deck/internal/tui [github.com/n-orlov/deck/internal/tui.test]
internal/tui/group_default_first_test.go:22:34: too many arguments in call to groupSortsBefore
	have (string, string, bool)
	want (string, string)
```
(and nine more identical-shaped errors against the same reverted signature,
truncated by `go vet`'s own "too many errors" cutoff). This is compile-time
API evidence only — it shows the test file's three-argument call requires
the landed `defaultFirst` parameter to exist at all, not that the ordering
behaviour behind it is absent; a removed parameter makes the package fail to
build regardless of what the removed code did.

Runtime behaviour evidence for the same ordering requirement comes from a
separate, compiling probe: the independent review's own revert kept
`groupSortsBefore`'s three-argument signature intact and instead restored
just its old default-last body (`internal/tui/group.go`, reviewer's patch
`artifacts/review/r139-order-reverted.patch`, applied over `b7d7b7d`):

```diff
@@ func groupSortsBefore(a, b string, defaultFirst bool) bool {
 	if a == "" {
-		return defaultFirst
+		return false // reviewer: unfixed default-always-last ordering
 	}
 	if b == "" {
-		return !defaultFirst
+		return true
 	}
```

With that body restored, the package builds and
`TestGroupOrderDefaultFirstFlagTrueMovesStructuralDefaultAloneToFront` runs
to completion — and fails on the ordering assertion itself
(`artifacts/review/r139-order-reverted.log`, exit status 1 in
`artifacts/review/r139-order-reverted.exit`):

```
=== RUN   TestGroupOrderDefaultFirstFlagTrueMovesStructuralDefaultAloneToFront
    group_default_first_test.go:112: group order (default_group_first=true) = [aaa Default zzz ], want [ aaa Default zzz]
--- FAIL: TestGroupOrderDefaultFirstFlagTrueMovesStructuralDefaultAloneToFront (0.00s)
FAIL
FAIL	github.com/n-orlov/deck/internal/tui	0.003s
FAIL
```

That runtime failure — the default group landing last (`[aaa Default zzz ]`)
instead of first (`[ aaa Default zzz]`) — is the actual proof the ordering
behaviour is absent without the fix; the build failure above is a separate,
weaker signal that only shows the API surface changed.

## Probe 3 — the config round-trip

**Test:**
`TestConfigFileUIDefaultGroupFirstDefaultsToFalseAndRoundTripsThroughWrite`
(`internal/config/config_test.go`) — absent-file default is `false`,
`[ui] default_group_first = true` in a hand-written file sets
`Settings.DefaultGroupFirst`, and a `FileConfig` write/re-read round-trips the
value while preserving an unknown key.

**Product hunks reverted:** the parse/write halves of commit `0ef480f`'s
plumbing only — `internal/config/toml.go`'s `setField` case
`"ui.default_group_first": cfg.DefaultGroupFirst = value` removed, and
`internal/config/toml_write.go`'s serialize case
`"ui.default_group_first": return strconv.FormatBool(cfg.DefaultGroupFirst)`
removed. The `FileConfig`/`Settings` struct fields, the schema row and the
default-value wiring were left in place so the package still builds — this
isolates the round-trip mechanism itself (a written/re-read key is silently
dropped) from a compile failure.

**Exact failure produced** (`ci/run.sh go test -count=1 ./internal/config/ -run TestConfigFileUIDefaultGroupFirstDefaultsToFalseAndRoundTripsThroughWrite -v`):

```
=== RUN   TestConfigFileUIDefaultGroupFirstDefaultsToFalseAndRoundTripsThroughWrite

--- FAIL: TestConfigFileUIDefaultGroupFirstDefaultsToFalseAndRoundTripsThroughWrite (0.00s)
```

## Disposition

All three probes fail against their respective reverted product hunks and
pass against the landed tree (`ci/run.sh go test -count=1 ./internal/tui/
./internal/config/` → `ok internal/tui 7.224s`, `ok internal/config 0.041s`).
R139 is audited: each of its three success-criteria assertions (group order
with the flag, live-apply through settings, the config round-trip) is backed
by a probe that genuinely exercises the fix rather than one that would also
pass against the unfixed tree.
